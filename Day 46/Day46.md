# 🐍 Day 46 — Database Migrations with Alembic

## Executive Summary

Database migrations provide version control for your database schema. As applications grow and business requirements evolve, database tables, columns, constraints, and indexes must change without destroying existing production data or requiring manual `ALTER TABLE` execution across development, staging, and production environments.

In Python backend engineering, **Alembic** is the standard migration tool designed specifically for **SQLAlchemy**. It tracks database schema history using revision scripts (`upgrade()` and `downgrade()`), allowing developers to roll forward or backward safely.

---

## Key Technical Concepts

### 1. Why Database Migrations?
- **Separation of Expectations:** Python ORM models represent application expectations. The physical database schema stores actual data tables. Modifying a Python model (e.g., adding `phone: Mapped[str]`) **does not** automatically alter the underlying database table.
- **Environment Synchronization:** Migrations guarantee that every environment (local, CI/CD, staging, production) applies identical DDL changes in exact chronological order.
- **Data Preservation:** Unlike dropping and re-creating tables (`Base.metadata.create_all()`), migrations execute incremental DDL statements (`ALTER TABLE`, `ADD COLUMN`, `CREATE INDEX`) while preserving existing database records.

---

### 2. Alembic Architecture & Core Files

When initialized via `alembic init alembic`, the following directory structure is created:

```text
day46/
├── alembic.ini              # Global configuration file (DB URL, logging)
├── alembic/
│   ├── env.py               # Migration environment script connecting Base.metadata
│   ├── script.py.mako        # Template for generating new revision files
│   └── versions/            # Chronological revision files (e.g., 001_initial_schema.py)
```

- **`alembic.ini`**: Defines global settings and points Alembic to the script location.
- **`env.py`**: Executes during `alembic upgrade` or `alembic revision`. It sets `target_metadata = Base.metadata` so Alembic can compare ORM model metadata against the current database schema.
- **`versions/`**: Contains Python scripts defining `upgrade()` (moving forward) and `downgrade()` (rolling back).

---

### 3. The Migration Lifecycle & Commands

```text
1. Modify SQLAlchemy ORM Model
               ↓
2. Generate Migration: alembic revision --autogenerate -m "describe change"
               ↓
3. Review Migration File in alembic/versions/
               ↓
4. Run Migration: alembic upgrade head
               ↓
5. Verify Database & Application
```

#### Essential Alembic CLI Commands:

| Command | Description |
| :--- | :--- |
| `alembic init alembic` | Initializes Alembic directory and `alembic.ini` |
| `alembic revision -m "msg"` | Creates a blank migration file |
| `alembic revision --autogenerate -m "msg"` | Compares ORM models with DB schema and generates migration DDL |
| `alembic upgrade head` | Applies all pending migrations up to the latest version |
| `alembic upgrade +1` | Applies next single migration step |
| `alembic downgrade -1` | Rolls back the most recent migration step |
| `alembic current` | Shows the revision ID currently applied to the database |
| `alembic history` | Displays chronological list of all migration revisions |

### 4. Autogenerate Pitfalls & Best Practices

> [!WARNING]
> Never blindly deploy autogenerated migrations to production without manual review!

Alembic `--autogenerate` detects:
- Table creations and deletions
- Column additions and deletions
- Column type changes and nullable flag changes
- Unique constraints and foreign keys

Alembic `--autogenerate` **may miss or misinterpret**:
- Table or column renames (often generated as `DROP COLUMN` + `ADD COLUMN`, causing data loss!)
- Custom enum type changes
- Table constraints with custom naming conventions
- Complex server default expressions

---

### 5. Schema Migrations vs Data Migrations

- **Schema Migration:** Changes table structure (e.g., `op.add_column('users', sa.Column('phone', sa.String(length=20)))`).
- **Data Migration:** Populates or transforms existing rows (e.g., setting default values for existing rows before applying `nullable=False`).

---

### 6. Database Indexes & Performance Optimization

An **index** is a B-tree data structure created on database table columns to enable rapid lookups ($O(\log N)$ instead of full table scans $O(N)$).

- **When to Index:** Columns frequently used in `WHERE`, `JOIN`, `ORDER BY`, or `GROUP BY` clauses (e.g., `users.email`, `products.name`).
- **Trade-off:** Indexes speed up `SELECT` queries but introduce slight overhead on `INSERT`, `UPDATE`, and `DELETE` operations due to index tree maintenance.

## ❓ Practice & Interview Q&A

### Q1: What is Alembic and why is `Base.metadata` required in `env.py`?
**Answer:** Alembic is the official database migration tool for SQLAlchemy. Setting `target_metadata = Base.metadata` in `env.py` gives Alembic access to all declared ORM models. Alembic compares `Base.metadata` against the current database schema to autogenerate accurate DDL migration scripts.

### Q2: What is the difference between `upgrade()` and `downgrade()` in Alembic?
**Answer:**
- `upgrade()`: Defines DDL statements to transition the database schema to a newer version (e.g., `op.create_table()` or `op.add_column()`).
- `downgrade()`: Defines inverse DDL statements to safely revert changes if a deployment needs to be rolled back (e.g., `op.drop_table()` or `op.drop_column()`).

### Q3: Why is modifying committed migration files bad practice?
**Answer:** Migration history is append-only. Once a migration script is committed and applied in team or production databases, modifying it creates schema hash discrepancies and breaks version history. Schema changes must always be appended as new revision files.
